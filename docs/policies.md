# 개발/운영 정책

## 브랜치 전략
- `main` = 운영(배포) 브랜치. 직접 푸시 금지 지향, PR로만 병합.
- `dev` = 개발 통합 브랜치. 모든 기능 개발은 여기서 출발.
- 기능 단위: `feature/*` → `dev` → (검증) → `main`.
- **main = 운영 서버 / dev = 개발 서버** 로 배포 환경을 분리한다(Railway/Render 환경 2개).

## 시크릿
- `.env`는 **절대 커밋 금지**. `.env.example`만 저장소에 둔다.
- API 키(오피넷/카카오/Anthropic)는 배포 플랫폼 환경변수로 주입.

## 외부 API 호출
- **오피넷**: 동일 (위치, 유종) 요청은 **1시간 캐시**(인메모리/Redis)로 호출 최소화. `aroundAll.do`는 KATEC 좌표 + 반경 ≤5km → 10km는 그리드 분할.
- **Claude API**: 출력 토큰 상한 설정, 프롬프트 캐싱 적용, 사실 데이터(가격/거리)는 도구 결과만 인용(환각 가드). 비용 모니터링.
- **카카오맵**: 무료 한도(월 300만) 내 사용, 키는 프론트 공개키/백엔드 REST키 분리.

## 알림/응답
- 가격/거리 등 숫자는 오피넷 원본만 표기. LLM 생성 숫자 금지.
- 결과 없음/조회 실패 시 사용자에게 명확히 안내(빈 화면 금지).

## 코드 품질
- Python: `ruff` 린트, 타입힌트 권장. 테스트는 `pytest`, 외부 호출은 목.
- 커밋: Conventional Commits (`feat:`, `fix:`, `docs:`, `chore:` …).
- 모든 PR은 테스트 통과 후 병합.
